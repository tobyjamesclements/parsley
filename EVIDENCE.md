# Evidence

One row per criterion in `SPEC.md`, in the same sections and the same order. Every criterion outside **Assumptions**
has a row; a row with an empty cell is an unmet criterion. Assumptions are permissions rather than obligations, so there
is nothing to evidence — taking one is a choice, and belongs in `DECISIONS.md`.

The column asks what would **catch a violation**, not what passes. Naming a test that would still be green if the
behaviour broke is worse than leaving the cell blank, because it hides the gap instead of showing it. Where nothing
executable catches a criterion, name what does — a build failure, a type signature, a specific review of a named file.

Test names below are `Class#method`. The *sabotage meta-tests* (`SabotageMetaTest`) are the proof that a named test
catches: each disables one guarantee in the engine (a hook the public API cannot reach) and asserts the suite fails.

## Liveness

| # | What would catch a violation |
|---|------------------------------|
| 1 | The oracle observes the *feed*, not the engine's acceptance (D41): `SimProcess#feedOne` reports every fed message before the engine sees it, so at quiescence `Oracle#checkAllReceivedDelivered` fails on any message fed in a committed step and never delivered — unless it lay in the ground-truth delivered causal past of the execution that fed it (the D31 clamp's sanctioned drops) — and the scenario fails on any non-empty hold-back buffer, across crashes, restarts, truncation, topic death and declaration churn. A process that failed closed, or whose channel is wedged below the earliest retained position, has its liveness (not safety) checks waived — the liveness premises are unmet there. Proof: `SabotageMetaTest#silentlyDroppingAFedMessageIsCaught` (an engine consuming a position and discarding its message — the omission the acceptance-gated oracle provably could not see), plus a 33/120-seed sweep margin for that sabotage. |
| 2 | Sending happens unconditionally inside `ParsleyProcessor#send` (review: it consults the engine only to stamp the header, no deliverability path exists); behaviourally, every property run emits from processes that simultaneously hold blocked messages — a send that waited on deliverability would deadlock the drain fixpoint and fail quiescence. |
| 3 | `TargetedScenarioTest#causeOnPositionThatNeverYieldsResolvesFromReadPositionReport` asserts *no* delivery before the read-position report and delivery immediately upon it — the whole simulator is clock-free, so an implementation relying on elapsed time cannot pass it; `EndToEndIntegrationTest#causeOnAbortedPositionsResolvesFromReadPositionReports` proves the same-lifetime trailing-aborted-run case end-to-end, and `#causeOnTrailingAbortedRunResolvesEvenAfterARestart` pins the restart case the audit showed the host's committed offsets never cover — resolved by the facts source's read_committed probe (D35), whose absence makes that test hang. |
| 4 | `TargetedScenarioTest#causeOutsideReceivedChannelSetDoesNotBlock` and `#depOnDeadIncarnationOfRecreatedTopicDoesNotBlock` fail on any hold; property runs routinely hand receivers metadata naming channels they do not receive, where a block trips the quiescence check. |
| 5 | `TargetedScenarioTest#heldMessageIsDeliveredAfterRestart` (simulated full restart from committed state), `EndToEndIntegrationTest#heldMessageSurvivesARealRestart` (real stop and restart over surviving local RocksDB state) and `EndToEndIntegrationTest#heldMessageSurvivesAStateDirWipeByChangelogRestore` (local state wiped, ordering state rebuilt entirely from the changelog) fail if the held message is lost or undelivered. Content fidelity of the restored hold — key, value, headers, timestamp exactly as received — is asserted by `SimProcess#drain` on every delivery in every simulated run, and pinned by `TargetedScenarioTest#restoredHeldMessageReachesLogicWithContentIntact` at a non-zero position (persisting empty headers or a zeroed timestamp in `StoreCodec#encodeHeld` fails both — mutations that previously survived the whole suite). Proof: `SabotageMetaTest#losingHeldMessagesAcrossRestartIsCaught`. |

## 2-safety

| # | What would catch a violation |
|---|------------------------------|
| 1 | Type-level: `Deliverability.decide`'s inputs are the causes, the received-channel set and the settled view — application state is not among its arguments, and `CorePurityTest` fails the build if the core package ever imports substrate, network or clock types it could smuggle state through. `ApiValidationTest#reservedStoreNamesAreUnconstructible` and `#storeNamesContainingTheReservedNamespaceAnywhereAreUnconstructible` fail if application state can alias ordering state — containment, not prefix: an embedded `__parsley.` composes a changelog inside the reserved namespace (`Store.of("q-__parsley.ordering")` under one process composes the ordering changelog of a sibling named `p-q`, which the prefix-only check accepted). The seam hands logic only declared stores: `TopologyWiringTest#stateReadFromAnUndeclaredStoreFailsClosedWithItsOwnReason` fails if an undeclared read is served instead of refused, and `#swallowedUndeclaredStoreReadStillFailsTheStep` fails if an application catch around its own handler can commit a step whose read was refused (the reader latches the refusal and the processor rethrows it after the handler returns). The latch holds across the whole delivery frame, not only the handler (D87): `#deserializerLatchedRefusalFailsTheStepEvenWhenSwallowed` fails if a refusal latched by the delivered payload's own deserializer — application code that runs before the handler — is erased by a frame reset, and `#serializerLatchedRefusalDuringPlanningFailsTheStep` fails if one latched during effect planning slips past the post-apply recheck. |
| 2 | `TargetedScenarioTest#restartDoesNotChangeWhatIsDeliveredOrItsOrder` runs the same script three ways — no restart, restart between steps, and a crash that discards uncommitted receipts, deliveries and emissions — and fails on any difference in what is delivered or its order; every property seed interleaves restarts and must stay oracle-clean; `EndToEndIntegrationTest#heldMessageSurvivesARealRestart` shows the real pause-only restart; `BootstrapIntegrationTest#expiredOffsetsRestartFromEarliestNotTheDeclaredLatest` fails if a restart after offset expiry changes what is delivered (skipping via the declared LATEST, or redelivering past the session floor). |

## Fault model

| # | What would catch a violation |
|---|------------------------------|
| 1 | Every property run and most targeted scenarios interpose dead positions (aborted transactions, `appendDead`) between messages; an implementation assuming consecutive positions misjudges the settled frontier and trips the oracle or the quiescence check within a few seeds. |
| 2 | The simulator has no clock at all — timeouts, leases and speed assumptions have nothing to read, and arbitrary pauses are exactly its random interleavings (a process can sit unscheduled for hundreds of events, then resume on stale state and be aborted); an implementation needing time bounds cannot pass `CausalOrderPropertyTest`. The resume-on-stale-state commit case rides on host fencing — see Host obligation 6; the stale-bootstrap variant is closed by mechanism, not by an empty-group check: initial positions are committed through one generation-fenced group membership (D48), and `BootstrapIntegrationTest#staleBootstrapCommitIsFencedByGroupMembership` forces a newer lifetime between the stale bootstrap's read and its commit on a real broker and fails if the stale commit lands. Expiry restarts re-establish earliest, never the declared LATEST (D36), pinned end-to-end by `#expiredOffsetsRestartFromEarliestNotTheDeclaredLatest` under a real offset deletion. |
| 3 | Property runs inject `crash()` at arbitrary points, including between receipt and delivery and between delivery and commit; `EndToEndIntegrationTest#crashMidStepDeliversEffectsExactlyOnce` crashes a real handler mid-message; both fail on any loss, duplication or misorder afterwards. |
| 4 | Same evidence as Fault model 1 plus `TargetedScenarioTest#causeOnPositionThatNeverYieldsResolvesFromReadPositionReport`: positions occupied by data the substrate never returns are the norm in the suite, not the exception. |

## Host obligations

These bind the host rather than your implementation, so the question is different. Say what your implementation does
when the host breaches the obligation, and what would catch it failing to do that. Where a breach cannot be detected
in principle, say so and state the blast radius — that is an honest cell, not a blank one.

| # | What your implementation does when this is breached, and what would catch it not doing so |
|---|-------------------------------------------------------------------------------------------|
| 1 | An out-of-order feed within an execution contradicts positions already covered and fails closed (`OUT_OF_ORDER_FEED`), including regressions at or below the session floor, which are never treated as replays mid-execution (D45); `ProcessEngineTest#refeedBelowSessionFloorIsDroppedAndWithinSessionFails` and `#inExecutionFeedRegressionFailsClosedEvenBelowTheSessionFloor` fail if the engine accepts either. Indefinite withholding is undetectable in principle (no bound distinguishes "late" from "never"); blast radius: delivery stalls on the affected channel and everything causally behind it — never a misordered delivery. |
| 2 | A report covering a message received-but-not-fed is undetectable at report time. If the covered message later arrives in the same execution, the engine fails closed — as `COVERED_POSITION_FED`, naming the report/feed contradiction and its two causes rather than blaming feed order (D77; `ProcessEngineTest#feedAtAReportCoveredPositionFailsClosedAsCoveredPositionFed` pins the reason); if it arrives in a later execution it is dropped as a replay (`TargetedScenarioTest#rewoundFeedIsDroppedNotRedelivered` catches the engine redelivering) — blast radius of a genuinely false report: that message is silently never delivered (liveness lost, safety kept; D10). A host that never reports (missing advances) stalls holds: `TargetedScenarioTest#causeOnPositionThatNeverYieldsResolvesFromReadPositionReport` asserts delivery happens *only* via the report, so a stall is the visible symptom, not a skipped cause. |
| 3 | Non-atomic commitment cannot be detected from inside a committed world — the engine only ever observes committed state. Blast radius: every safety property, which is why the step machinery is verified where it can be: the simulator's transactional store aborts and rolls back in every property run, and `EndToEndIntegrationTest#crashMidStepDeliversEffectsExactlyOnce` checks state, sends and read positions really do commit together on the real host. |
| 4 | A host resuming a process in place after an abort, without re-feeding, cannot be detected in general: it produces no contradictory feed, and it is not merely a pause — the aborted step's deliveries and emissions vanish from committed history silently. Detected subset: contradictory feeds after a resume trip the session floor and fail closed (row 1's test). The simulator deliberately offers no resume-in-place operation (`SimProcess#crash` documents why). Blast radius of the undetectable remainder: lost deliveries/emissions for the aborted step — a liveness loss under host breach, never a misordered or duplicated delivery. |
| 5 | Resume-from-committed with re-feed of the uncommitted is exercised by every simulated crash and by the real restart tests; the engine's dedupe (session floor) and rollback (store transactionality) fail the oracle's Safety 1/2 checks if the implementation mishandles either side. A host that re-feeds *more* than the uncommitted is handled as row 2's replay case. The detectable breach shape — committed read positions the bootstrap did not stamp, with no ordering changelog behind them, so the state observed at initialisation cannot be the state of the last committed step — refuses at start (`ORDERING_STATE_LOST`, D76): `BootstrapIntegrationTest#lostOrderingChangelogWithSurvivingOffsetsRefusesToStart` fails if that start silently resumes with an empty engine, `#emptiedChangelogWithSurvivingOffsetsRefusesToStart` fails if the changelog surviving as a topic while its records are purged slips past the same refusal — prior state is keyed on ordering records, not topic existence (D84) — `#emptiedChangelogPartitionWithSurvivingOffsetsRefusesToStart` fails if one purged partition of a multi-partition changelog escapes it (the loss is per task, D88) — `#lostChangelogWithOffsetsOnAFormerlyReceivedTopicRefusesToStart` fails if a declaration change alongside the loss hides a formerly-received partition's evidence, and `#bootstrapCommittedOffsetsWithoutAChangelogStillStart` fails if the refusal overreaches into first-start bootstrap crash recovery. |
| 6 | A superseded execution's step committing cannot be prevented locally; the implementation relies on the host's transactional fencing, and everything a zombie does before fencing is rolled back ("has not occurred"). Honestly: no test in this suite creates a superseded execution, and the crash test's aborted step carries no output record, so a fencing breach would not surface here — the exactly-once test exercises the fencing machinery (zombie transaction abortion on restart), not the breach. Blast radius if the host truly broke fencing: duplicate deliveries and sends — Safety 2 falls with the host's obligation, and only host-side accounting could reveal it. |
