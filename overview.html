Parsley provides causal delivery order for Kafka Streams processors. When the required conditions hold, every wrapped processor observes records in causal order even when they originate from several topics and partitions: if an event A causally precedes an event B, a processor subscribed to both of their topics processes A before B. Parsley achieves this by stamping each record with its producer's causal dependencies and buffering a record until those dependencies have been observed locally.

The guarantee is the causal-consistency model of the distributed-systems literature (Lamport's happened-before relation, realised with vector clocks), instantiated on Kafka's own coordinates: a clock is indexed by (topic, partition) rather than by process, and its values are broker offsets. Internally the implementation is a stack of three protocols, presented in the module style of Cachin, Guerraoui, and Rodrigues: a channels layer that adapts Kafka topic-partitions into reliable FIFO channels, a causal broadcast layer (Birman–Schiper–Stephenson) that delivers in causal order, and a gossip layer (Chandy–Misra–Bryant null messages) that keeps causal progress observable through non-emitting processors. The documentation site develops the theory and the three protocols in full; this page describes the public API.

The entire public surface lives in a single package, {@link io.github.tobyjamesclements.parsley}. The topology-level entry point is three roles mirroring Kafka Streams' own {@code StreamsBuilder} / {@code Topology} / {@code KafkaStreams}: {@link io.github.tobyjamesclements.parsley.CausalStreamsBuilder} declares the topology's single causal stage, the fluent chain's terminal {@code .build()} produces a {@link io.github.tobyjamesclements.parsley.CausalTopology}, and {@link io.github.tobyjamesclements.parsley.CausalStreams} is the runtime that wraps the underlying {@code KafkaStreams} instance. The low-level processor decorator that powers it, {@code ParsleyProcessorSupplier}, is package-private internal machinery, not constructed directly.

Joining a running topology needs no coordination: a new application simply starts consuming, its replay self-gates into causal delivery order through the ordinary hold-back queue, and its truthful stamps make its outputs correctly gated everywhere from its first emission. Parsley has no configuration keys at all; startup fails if any {@code parsley.*} key is present.

Core concepts

Causal dependencies
The positions a consumer must have observed before a record stamped with them may be delivered. They are a producer's snapshot of what it had seen when it sent the record. They are carried as {@link io.github.tobyjamesclements.parsley.CausalClock} in a {@code parsley-causal-clock} header. Build one from a consumed record by starting with {@link io.github.tobyjamesclements.parsley.CausalClock#using(java.util.Properties) using} to bind a topic resolver, then folding in each record with {@link io.github.tobyjamesclements.parsley.CausalClock#observe observe}. Combine several for a fan-in with {@link io.github.tobyjamesclements.parsley.CausalClock#merge merge}, and attach the result to an outbound record with {@link io.github.tobyjamesclements.parsley.CausalClock#stamp stamp}. When consuming a topic a Parsley topology produces, fold every record in with {@code observe} but skip those for which {@link io.github.tobyjamesclements.parsley.CausalClock#isNullMessage isNullMessage} returns true, which are protocol metadata rather than business records.
The delivery gate
A record is delivered once this node's own contiguous frontier, the positions it has itself delivered gap-free, dominates the record's dependencies on the coordinates it consumes. A peer's advertised claim never substitutes for local delivery, which is the Birman–Schiper–Stephenson delivery condition. A dependency naming a coordinate this node does not consume is ignored, unconditionally: this is sound because stamps are transitively complete and merged unconditionally, so any consumed causal ancestor is claimed directly in the same clock, and each ignore is counted by a metric rather than treated as a failure. The frontier is internal to Parsley's processor machinery and is not a separate public type.
Protocol null message
A record with a null value, carrying the triggering record's key and a {@code _parsley_null_message} header, that carries a node's completeness frontier downstream when a delivered input produced no business output. Parsley routes each null message to the emitting task's own partition on every sink; the key is informational only. It keeps causal progress flowing through filters and not-yet-emitting aggregates, and a received null message is relayed further downstream only when its carried clock advanced this node's knowledge of a channel it consumes, never unconditionally, which is what keeps a cyclic topology's marker traffic from circulating forever. Parsley's processors handle null messages internally; a plain Kafka client detects them with {@link io.github.tobyjamesclements.parsley.CausalClock#isNullMessage isNullMessage}.
Causal buffer
Records whose dependencies are not yet satisfied are held in an unbounded, changelog-backed buffer and released as soon as the frontier catches up. There is no configuration that trades causal order for liveness: a record that cannot be evaluated at all, an undecodable payload or an undecodable causal-clock header, unconditionally fails the task rather than being dropped, evicted, or delivered out of order.

Entry points

The public entry-point types and their roles
TypePurpose
{@link io.github.tobyjamesclements.parsley.CausalStreamsBuilder}Declares the topology's single causal stage: {@code stream(...)} one or more source topics, {@code .process(supplier)} to bind them to a causal-decorated processor, {@code .to(...)} to declare its sink(s). The chain's terminal {@code .build()} produces a {@link io.github.tobyjamesclements.parsley.CausalTopology}.
{@link io.github.tobyjamesclements.parsley.CausalTopology}The built causal topology, a specification rather than a real Kafka Streams {@code Topology}, ready for {@code new CausalStreams(topology, props)}.
{@link io.github.tobyjamesclements.parsley.CausalStreams}The runtime: wraps the underlying {@code KafkaStreams} instance, and owns graceful causal drain on {@code close()}.
{@link io.github.tobyjamesclements.parsley.CausalClock}Stamps and reads causal dependencies directly on plain {@code ProducerRecord} and {@code ConsumerRecord} objects, for talking to a Parsley topology from outside Kafka Streams.

Typical usage

{@code
CausalTopology topology = new CausalStreamsBuilder()
        .stream(List.of("c1", "c2"), Serdes.String(), orderSerde)
        .process(new EnrichOrderSupplier())
        .to("c3", Serdes.String(), enrichedSerde)
        .build();

CausalStreams causalStreams = new CausalStreams(topology, props);
causalStreams.start();
Runtime.getRuntime().addShutdownHook(new Thread(causalStreams::close));

// At the edge, from a plain Kafka client
CausalClock deps = CausalClock.using(props).observe(consumedRecord);
producer.send(deps.stamp(new ProducerRecord<>("c3", key, value)));
}
