# Parsley pre-vendoring audit report

**Date:** 2026-08-10 · **Scope:** core ordering engine + Kafka layer, audited across seven dimensions against SPEC.md, docs/, and DECISIONS.md · **Method:** per-dimension code hunts with empirical probes, each finding passed through two independent adversarial refuters · **Refuted and dropped during verification:** 2

---

## 1. Executive summary

**Verdict: ready-with-fixes.** The core delivery engine (`Deliverability`, the frontier/settled-position math, the hold-back buffers, the wire codec) survived a genuinely deep hunt with zero confirmed defects — the causal guarantee as implemented in `core/` is sound in every supported configuration. The defects that did survive adversarial verification all live at the seams: EOS task-lifecycle hygiene in the processor, corrupt-state classification at store decode, and fault isolation in the facts source. All four confirmed findings have small, local fixes.

One confirmed finding is **critical** and must be fixed before vendoring: a facts round computed from an aborted transaction's in-memory state survives Kafka Streams task revival in processor instance fields and, applied to the rolled-back engine, can deliver an effect before its cause and then silently drop the cause forever (F1). This is a reachable Safety 1/Safety 3 violation with silent data loss on the pinned Streams version — the exact class of failure this library exists to prevent. The fix is a few lines (reset the round in `init()` or incarnation-tag it).

The three confirmed majors are resilience gaps, not guarantee violations: a truncated store restore is silently trusted instead of failing closed (F2), corrupt changelog blobs crash unclassified or attempt multi-GiB allocations instead of raising the designed refusal (F3), and one sick partition starves every channel's fact ingestion — including mandated fail-closed stop signals — for the duration of the outage (F4). Each fix is local and matches patterns the codebase already uses elsewhere.

Recommended gate: fix F1–F4 and add the two highest-priority tests (§3, T1–T2) before the vendor clone. The contested and minor findings below are worth triaging but do not block.

## 2. Findings

#### F1 · CRITICAL — Processor instance state survives EOS task revival; a stale facts round asserts rolled-back feed progress as durable truth

`src/main/java/io/github/tobyjamesclements/parsley/kafka/ParsleyProcessor.java:58` (root cause), with `:97-132` (`init()`), `:204-212` (`probeHints()`), `kafka/AdminFactsSource.java:306-374`, `core/ProcessEngine.java:324-328`

`gathered` and `gatherInFlight` are instance fields (lines 58–61) that `init()` never resets, and the class has no `close()`. `probeHints()` snapshots the engine's **in-memory** `fedUpTo`, which includes records fed inside the currently open, uncommitted EOS transaction. Verified from the pinned Kafka Streams 4.3.1 bytecode: a plain `TimeoutException` on commit triggers `closeDirtyAndRevive`, which retains the task object and re-calls `init` on the **same** `ParsleyProcessor` instance against the rolled-back (restored) engine. A gather launched by the previous incarnation completes on the runtime-scoped executor and deposits its result into the surviving field; `AdminFactsSource.probeTrailingRuns` guards only the case where the committed offset is *ahead* of the hint (lines 318–320), never the rollback case where the hint outran durable state, and merges the probe report via `Math::max` (line 371). `ProcessEngine.onFacts` then durably applies it as "fed or never arriving." No epoch or generation ties a `PositionFacts` round to the execution whose in-memory state informed it.

**Failure scenario (refuter-replayed):** committed `fedUpTo(c)=50`; message *m* held with cause `(c,90)`; an aborted upstream run occupies `c@101..110`. Incarnation 1 feeds real `c@51..100` in-transaction, hints `{c:100}`, the commit times out, the task is revived (state restored to 50). The gather completes: probe seeks `c@101`, finds first record at 111, reports `committedNextRead(c)=111`. The revived incarnation applies the round: `advanceFedUpTo(c,110)` — covering real, will-be-refed records 51..100. The punctuator drains: *m* is delivered before its cause `c@90` and committed. Re-fed `c@51` then hits `OUT_OF_ORDER_FEED`; after the next restart the session floor rebuilds at 110 and `c@51..100` — including the cause — are silently `DUPLICATE_DROPPED`. Effect before cause, fifty real records never delivered, no failure surfaced. Even the benign interleaving is a spurious permanent fail-closed stop with a misleading diagnosis. Reachability is broader than the worst case: the poison only needs a trailing transaction marker beyond the in-memory fed position, which is the near-permanent state of a channel tail under transactional producers.

Both refuters confirmed independently, including the Streams-internals claims, and noted `runtime.md`'s zombie-safety argument does not cover this: the poisoned fact escapes the aborted transaction through a processor field. SPEC Host obligation 2's soundness condition is breached by Parsley's own Kafka layer.

**Fix direction:** in `init()`, clear `gathered` and reset `gatherInFlight` (or stamp each round with an incarnation counter checked at apply time). Consider adding `close()` to do the same.

**Merged (same root cause — re-init of the same processor instance without reset):** every `init()` also schedules an *additional* wall-clock punctuator (line 123, `Cancellable` discarded, no `close()` override); verified from Streams 4.3.1 bytecode that the punctuation queues survive revival, so after N revivals each task runs N+1 facts punctuators per interval — multiplying admin/probe load against an already-struggling broker and widening the window in which a stale round is applied. Minor on its own; fixed by the same `init()`/`close()` hygiene (cancel the previous punctuator).

#### F2 · MAJOR — A store missing its version entry but containing ordering state is silently re-stamped v1 and trusted

`src/main/java/io/github/tobyjamesclements/parsley/core/ProcessEngine.java:127`

The constructor treats a null version entry as a fresh store and stamps `STORE_FORMAT_VERSION` without checking whether the store already holds parsley state; the `UNKNOWN_ORDERING_STATE_FORMAT` refusal (lines 129–131) fires only when a version entry *exists* with wrong content. The `v` record and the `n` name bindings are written exactly once, in the earliest transactions, so they live at the head of the changelog. Empirically confirmed: build held state, delete only the `v` key (and `n` bindings), restart — the engine proceeds, restores the surviving holds, re-stamps v1, and silently re-binds every topic name via the `bound == null` path (lines 137–138), **disarming the D33 recreated-topic protection**. `ParsleyRuntime.refuseStrandedHeldMessages` reads the entire changelog at startup but never inspects the `v` key, so the evidence is in hand twice and ignored twice.

**Failure scenario:** an operator alters the `__parsley.ordering` changelog's `cleanup.policy` away from the compact that `ProcessTopology.java:94` requests, the oldest segment ages out, and a node without local state restores the remainder: version and name bindings gone, recently-rewritten `f`/`c`/`p`/`h` records surviving. The process runs on a frontier/`fedUpTo` missing every entry not rewritten since the lost segment — later sends under-express causes with no failure anywhere. Both refuters confirmed the sharpest point: under faithful compact-only operation a data-bearing store with no `v` is *impossible*, so the missing check has **no false-positive path** — a null version alongside parsley-tagged data is unambiguous evidence of state loss. The gap also softens the format-version tripwire a vendored fork will rely on when it bumps the store format. No DECISIONS.md entry accepts this; D38 explicitly rejects "documenting the gap" for silent state loss.

**Fix direction:** in the constructor, if `version == null` and any parsley-tagged record exists (one bounded prefix probe), throw `UNKNOWN_ORDERING_STATE_FORMAT`. Separately worth considering: verify the changelog topic's actual `cleanup.policy` at startup alongside the existing width check.

#### F3 · MAJOR — Store decode paths trust wire length/count fields: unbounded allocation, and corruption escapes the fail-closed classification

`src/main/java/io/github/tobyjamesclements/parsley/core/StoreCodec.java:247` (primary), `:236`, `:241`, `:245`, `:264`

`decodeHeld` allocates arrays and `ArrayList` capacity sized directly from ints read off the blob with no check against `buffer.remaining()`, and its corruption catch (line 264) lists only `BufferUnderflowException | IllegalArgumentException | IndexOutOfBoundsException`. Empirically confirmed against the compiled class: key-length −2 → `NegativeArraySizeException` (a direct `RuntimeException` sibling of the caught types — escapes); key-length `Integer.MAX_VALUE−2` → attempted ~2 GiB allocation → `OutOfMemoryError`; header-count `Integer.MAX_VALUE` → `OutOfMemoryError: Requested array size exceeds VM limit` (heap-independent); a truncated blob correctly raises the designed `ParsleyFailClosedException(UNKNOWN_ORDERING_STATE_FORMAT)` — proving these inputs bypass the intended path. The method's own Javadoc (lines 219–222) promises the refusal for a blob that "is corrupt"; `CausesCodec.decode` shows the repo's own standard (count validated against `remaining()` before allocation). The blob arrives verbatim from the `__parsley.ordering` changelog via Streams restoration, decoded at `ProcessEngine.java:162` and `:459` with no broader catch — a misdirected producer or corrupted record in that topic reaches this code.

**Failure scenario:** one corrupted length field in a changelog record; on the next restart the stream thread dies with `NegativeArraySizeException` — `status()` shows no `refusalReason`, `stoppedDeliberately()` is false, so a supervisor keyed on D55's branch treats a permanent corrupt-state condition as transient and crash-loops with no Parsley diagnosis — or the JVM attempts a ~2 GiB allocation from 4 bytes of input, an `Error` whose blast radius in the vendored shared JVM exceeds Parsley's documented whole-process bound. The process does still stop (correctly major, not critical), but the fail-closed *diagnosis* contract of docs/failing-closed.md is defeated.

**Fix direction:** validate every length/count against `buffer.remaining()` before allocating (the `CausesCodec` pattern) and add `NegativeArraySizeException` to the catch — or catch `RuntimeException` in this method, since the contract is total.

**Merged into this finding (same root cause — store-decode paths below the strictness standard the wire codec sets; the first two empirically confirmed, reported minor, not adversarially verified):**

- **Restore-scan key/value parsers unwrapped** (`ProcessEngine.java:148-166` → `StoreCodec.channelOfKey`, `positionOfHeldKey`, `decodeLong`): malformed `f`/`c`/`p`/`h` keys or values crash with raw `IndexOutOfBoundsException`/`BufferUnderflowException` instead of the classified refusal — same empty-`refusalReason` supervisor misclassification as above.
- **`decodeHeld` accepts trailing garbage** (`StoreCodec.java:263`): the buffer is never checked for full consumption; `encodeHeld` writes exact-size, so trailing bytes are per se corruption evidence, currently ignored — in the worst shape a shrunk inner length field restores a held message whose bytes differ from what was received, silently breaking state.md's byte-for-byte promise.
- **Contested — `decodeLong` accepts any length** (`StoreCodec.java:138`): a 12-byte `fedUpTo` value silently restores as its first 8 bytes; a 4-byte value escapes as raw `BufferUnderflowException` (both empirically confirmed). One refuter confirmed in full; the second argued unreachability — every writer emits exactly 8 bytes, and RocksDB block checksums plus Kafka record CRCs crash below Parsley before a wrong-length value with a valid CRC can be presented — making the check near-zero marginal detection. Both agree the code fact is real; the dispute is whether it is major or a two-line symmetry hardening. Since the fix is two lines and F3's fix touches the same file, close it in the same pass.

#### F4 · MAJOR — One unavailable partition blacks out the entire facts round, indefinitely deferring mandated stop signals

`src/main/java/io/github/tobyjamesclements/parsley/kafka/AdminFactsSource.java:200`

`gather()` aggregates every channel's earliest-offset query through `ListOffsetsResult.all().get(10s)` (verified from the pinned kafka-clients 4.3.1 jar: `all()` fails if *any* partition future fails). A single leaderless partition (RF=1 broker down — within the stated deployment assumptions) makes the whole round throw before the `PositionFacts` at line 240 is constructed, and both callers (`ParsleyProcessor.java:149-159`, `:214-228`) drop the round whole. `describeTopics` is metadata-only and still succeeds for a leaderless topic, so the sick channel is never filtered out of the batch; the failure repeats every interval for the outage's duration. Critically, the round is also the **only mid-run carrier of the sticky dead/recreated verdicts** — `engine.onFacts` is the sole mid-run path to `CHANNEL_IDENTITY_CHANGED` — so verdicts already computed earlier in the round are discarded with it.

**Failure scenario:** process P receives topics R and X; X has a leaderless partition for an hour. During that hour: (1) R is deleted, recreated under the same name, and refilled past P's committed position — the recreated verdict is computed and set sticky, but never reaches any engine, so the new incarnation's records are adopted under the old identity for the *full hour* instead of the "facts interval plus metadata propagation" window D44 records; (2) every held message on every channel loses its release path; (3) the `POSITIONS_DISCARDED_UNREAD` defense receives no log-start facts. One sick partition couples all channels' evidence acquisition and defers a mandated fail-closed stop unboundedly — contradicting D22's per-channel withholding granularity and D44's recorded bounds. Both refuters confirmed; the per-future `describeByNames` handling in the same file shows the `.all()` asymmetry is oversight, not decision. (The claim's "under-min-ISR" aside is wrong — min-ISR gates produces, not offset reads — but the leaderless mechanism fully stands.)

**Fix direction:** switch to `ListOffsetsResult.partitionResult` per partition, confining the loss to the affected channel; ensure dead/recreated verdicts are carried by the round even when position queries partially fail.

### 2.2 Contested (mechanism verified; one refuter dissented on severity/reachability)

Both of these were empirically demonstrated; the dissent in each case is about consequence, not code fact. Recommended disposition: apply the cheap hardening, do not treat as blockers.

**C1 — Held-buffer restore trusts an iteration order `OrderingStore.scanPrefix` never promises** (`core/ProcessEngine.java:154`, `core/OrderingStore.java:38-44`). The restore appends holds in scan-visitation order and every downstream mechanism (settled = head−1, heads-only offering, head-check delivery) assumes the deque head is the minimum held position — but the seam's javadoc promises only visitation, not order. Demonstrated: a contract-conforming reverse-order store wrapper produced a silent Safety 1 + Safety 3 inversion with no diagnostic. The dissent: every supported configuration is ordered (Parsley builds its own Bytes-keyed RocksDB store, never exposed per D11; the sim store is an ordered TreeMap), the ordering is documented in docs/state.md and StoreCodec's javadoc, and reaching the failure requires the integrator to author new incorrect storage — so this is a documentation/hardening item, not a major. Given the stated audience is a vendoring integrator implementing or wrapping seams, the cheap fix is worth taking: add the order clause to `scanPrefix`'s javadoc and a per-channel position-monotonicity assertion in the TAG_HELD restore scan that raises `UNKNOWN_ORDERING_STATE_FORMAT`.

**C2 — Header-aware application serializers bypass the reserved-header refusal** (`kafka/ParsleyProcessor.java:296-302`, `api/Effects.java:41-51`). The `parsley.*` refusal runs only at `Effects.Emission` construction; `send()` then hands mutable `RecordHeaders` to the application's 3-arg `Serializer.serialize` and appends the genuine `parsley.causes` stamp afterwards with no re-validation. Demonstrated via TopologyTestDriver: a header-writing serializer produced a forwarded record with two `parsley.causes` headers plus a smuggled `parsley.*` header — an emission docs/wire-format.md says must be refused, and one that permanently fail-closes every downstream receiver (`extractCauses` duplicate branch, `UNDECODABLE_METADATA`). The dissent: because the stamp is appended *after* the serializer runs, the serializer can never strip or replace the real stamp — the worst case is a detectable poison record that fails closed at the receiver, a wire condition the sim already generates and verifies (D43), and the trigger requires application code writing into a documented reserved namespace; so at most minor, unlike the fail-open interceptor hole D51 closed. Both readings agree a one-line post-serialize header re-check in `send()` improves failure locality (sender-side `RESERVED_HEADER_USED` instead of a poisoned topic); take it.

## 3. Test gaps — prioritized additions

One test-adequacy claim was **partially refuted** during verification and is corrected here before it misleads: the assertion "no test ever restores the ordering store from its changelog" is false. `EndToEndIntegrationTest#crashMidStepDeliversEffectsExactlyOnce` forces a dirty task close under EOS; restore-machinery logging confirmed the second run rebuilds the store entirely from the changelog ("did not find checkpoint offset … Finished restoring changelog … 3 records"). Likewise, Streams 4.3.1 hardcodes `cleanup.policy=compact` for unwindowed KV changelogs, so the hypothesized one-token regression does not produce a delete-policy changelog. What survives of that finding is real but smaller: docs/verification.md:31's "store persistence across driver restarts" is backed by no test (both wiring tests build one driver), EVIDENCE.md Liveness 5's "RocksDB + changelog" citation is half-unbacked, and nothing asserts the changelog's policy or exercises an explicit state-dir wipe. Those become T2 below.

Priority order (P1 = before vendoring, P2 = first post-vendoring hardening sprint, P3 = opportunistic):

1. **P1 — Task-revival regression test guarding the F1 fix.** No test in the repository exercises `closeDirtyAndRevive`/re-`init` of a live processor instance — the exact path the critical finding lives on and the fix must be pinned on. TopologyTestDriver cannot reach it; either drive `StreamTask` revival directly against a real embedded broker (induce a commit timeout), or unit-test the processor contract (`init()` must observe no round from a prior incarnation — inject a poisoned `gathered` and assert it is discarded). Also asserts single-punctuator-per-incarnation.
2. **P1 — Explicit changelog-recovery test + config assertion.** An `EndToEndIntegrationTest` variant that wipes the state dir between the two `Parsley.start` calls and asserts the held message still delivers (making changelog recovery a *named, deliberate* assertion rather than a side effect of the crash test); a `BootstrapIntegrationTest` assertion that `<appId>-__parsley.ordering-changelog` exists with `cleanup.policy=compact` (this is also the natural home for F2's runtime policy check). Correct docs/verification.md:31 and EVIDENCE.md Liveness 5 while there.
3. **P1 — Corrupt-store-entry fail-closed tests pinning the F3 fix:** negative and oversized length fields, oversized header count, wrong-length `f`/`c`/`p` values, malformed keys, trailing bytes — each asserting `ParsleyFailClosedException(UNKNOWN_ORDERING_STATE_FORMAT)` and a populated `refusalReason`. Plus the F2 probe (data-bearing store, `v` key deleted → refusal) as a permanent test.
4. **P2 — Two-instance / task-migration smoke test** (contested priority: one refuter argued EOSv2 fencing is host machinery tested upstream, and a migrated task runs the identical library path as a restarted one, which *is* tested). EVIDENCE.md Host obligation 6 concedes no test creates a superseded execution. A single smoke test — two instances of one app, close one so a task holding an undelivered effect migrates, assert holds survive and nothing redelivers — is cheap insurance on the one leg of the documented "restarts, rebalances and partition reassignment" guarantee no test crosses, and would also exercise F1's territory.
5. **P2 — SabotageMetaTest hardening:** `ignoringTruncationIsCaught`, `ignoringRecreationIsCaught` and `deliveringPastDeadChannelHoldsIsCaught` assert only `assertDoesNotThrow` (they prove the sabotage disarms the refusal, not that anything catches the violation); add oracle-violation assertions with pinned seeds, and add `DELIVER_PAST_DEAD_HOLDS` to the random-sweep floors (currently zero randomized catch evidence). Align docs/verification.md:25-27 with reality.
6. **P2 — Facts-source resilience tests:** per-partition degradation (one leaderless partition must not suppress other channels' facts or the dead/recreated verdicts — pins the F4 fix, injectable via the overridable admin seams D50 established) and debounce continuity (NAME_GONE → hours of UNAVAILABLE → NAME_GONE must *not* confirm death — pins M4, via the injected clock).
7. **P3 — CorePurityTest:** use `Files.walk` (currently non-recursive — a future `core/` subpackage escapes entirely) and widen the banned list (`java.util.Date` import form, `Random`/`ThreadLocalRandom`/`Math.random`, `Thread.sleep`, `java.io.`/`java.nio.file`, `System.getenv/getProperty`). Cheap, and it guards the sim's determinism promise against exactly the debug-aid additions vendoring integration invites.
8. **P3 — Oracle delivery-time legality check:** the oracle verifies relative order among delivered pairs, so a premature delivery whose cause first arrives after a restart is buried by the engine's `deliveredPast` clamp plus the oracle's D41 exemption acting together. Check each `trueCause` is delivered/settled/exempt at the moment of `onDelivered`; closes the composite blind spot without disturbing D41.
9. **P3 — Broker-bounce integration test.** Contested down from major: verification showed the feared "outage matures into evidence" path is structurally unreachable (`describeByIds` rethrows connectivity errors before the verdict loop runs; a dead verdict requires affirmative broker answers; the core has no clock), and the debounce is pinned deterministically at its designed seams with fact starvation covered in the sim. A bounce test remains worthwhile belt-and-braces for the reconnect/recovery plumbing, but is not a gap in the guarantee's evidence.

## 4. Completeness

**Dimensions that produced confirmed findings** — state-recovery (F2), wire-format (F3), eos-processor (F1), facts-source (F4) — each also documents substantial clean-hunt territory in its notes; their coverage was deep enough to both find real defects and bound them.

**Dimensions with zero confirmed findings:**

- **delivery-correctness — silence earned.** The full decision path was read (`Deliverability`, `ProcessEngine`, `Causes`, codecs, host call order, both unit suites, SPEC + docs + all delivery-bearing DECISIONS), with nine specific hunts each closed by explicit reasoning: frontier off-by-ones checked against docs/delivery.md including the position-0 edge; transitive coverage of the compressed frontier verified including engine/oracle agreement; channel ordering consistency across comparator, byte encoding, and store scans; the `deliveredPast < head` invariant proven so the join clamp cannot skip a hold; session-floor dedup vs. re-feed vs. dead-channel ordering; every release path traced to evidence; restart determinism of all decision inputs. Targeted suites were run, and the one suspicion this hunt did raise was pursued to an empirical demonstration (the C1 reverse-scan experiment) rather than filed on speculation. This is the audit's strongest cell, appropriate for the code that carries the guarantee.
- **rebalance-membership — silence largely earned, one caveat.** All 71 DECISIONS records were read; the D48 bootstrap fencing was walked against broker semantics across five adversarial interleavings; close/shutdown, zombie, and shared-state hunts were closed with reasoning, and known residuals were verified as deliberately recorded before being excluded. Two caveats: this dimension ran as a static audit (tests not executed), and the Kafka client behaviors underpinning M2 were asserted from client semantics rather than reproduced — the reviewer says so and asks for a broker repro. Treat M2 as credible-unverified.
- **test-adequacy** produced findings (§3) rather than silence; its coverage notes show the sim harness, oracle, and all four integration classes were read in full, and its self-corrections (e.g. the changelog-restore refutation) indicate the verification layer was working.

**Areas no dimension owned:**

- **`api/` package** — touched incidentally (`Effects`, `Delivery`, `ParsleyConfig` sections, `ApiValidationTest` method inventory) but no dimension performed a dedicated hunt over declaration validation, the serde surface, or `Parsley.start`'s public contract. Given `ParsleyConfig`'s deny-list is load-bearing for two findings (M2's suffix-match gap; D51's interceptor ban), a focused pass over `api/` validation is the most valuable uncovered ground.
- **Build/packaging** — `pom.xml`, wrapper, CI, dependency pins (beyond the Streams 4.3.1 bytecode checks done ad hoc) were reviewed by no dimension. Since vendoring means adopting the build, the employer should do its own dependency/supply-chain pass; D19's upgrade-revalidation mandate should be carried into the fork's process.

**Residual risks the audit confirmed are recorded and accepted (carry into the fork's operator docs, no code change filed):** wholesale changelog record loss while the topic and group offsets survive is undetectable at the store seam (F2's fix narrows but cannot close it — durable provenance outside the store is unavailable per D33/D36); an operator forward-resetting group offsets while the process is stopped forges the host's canonical read-position report (D6 assumption breach); concurrent multi-instance cold-start collisions (D48's recorded residual).

**Verification honesty:** two findings were refuted outright and dropped during adversarial review; one plausible finding was partially refuted and demoted to documentation/test corrections (§3); two others were demoted on consequence with the dissent recorded rather than suppressed (§2.2). The confirmed set above is the residue of that process, and each confirmed finding was independently reproduced or bytecode-verified by both refuters.
